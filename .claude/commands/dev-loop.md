# /dev-loop — 지속 개발 사이클 (1회 = 백로그 1건)

너는 이 사이클의 Director다. 직접 코드를 고치지 말고 서브에이전트에 위임하라.
반복 실행은 이 명령을 `/loop`(대화형 세션) 또는 크론/스케줄러(원격 세션)로 감싸서 돌린다 — 이 명령 자체는 **정확히 1건만** 처리하고 끝난다.

상세 규칙은 `AGENT_HARNESS_GUIDE.md`가 기준이다: 판정 기준(§2.1), 검증 게이트 G1~G6(§3), 작업 유형별 라우팅(§4), 위임 프롬프트 템플릿(부록 A). 아래 절차와 지침서가 충돌하면 지침서를 따른다.

## 절차

### 0. 안전 점검 (하나라도 걸리면 즉시 중단하고 사유 보고)
- `git status`가 깨끗하지 않으면 중단 (이전 사이클 잔여물 오염 방지).
- `DEV_BACKLOG.md`의 **중단 플래그** 섹션에 `STOP`이 적혀 있으면 중단.
- 직전 로그(`DEV_LOOP_LOG.md`)의 마지막 두 항목이 연속 실패면 중단하고 사용자 확인 요청.

### 1. 작업 선택
- `DEV_BACKLOG.md`에서 첫 번째 미완료 항목(`- [ ]`)을 고른다. `$ARGUMENTS`로 번호가 지정되면 그 항목.
- 미완료 항목이 없으면: "백로그 소진 — 루프 종료"를 보고하고, 크론이 돌고 있으면 크론을 삭제한 뒤 끝낸다.
- 항목이 `⏸`(보류) 또는 `❓`(결정 대기) 표시면 건너뛰고 다음 항목.

### 2. 구현 — de-coder 서브에이전트에 위임
- 항목 내용 + 관련 파일 경로 + 완료 기준을 명확히 적어 위임한다.
- 검증(node --check 등)까지 포함해 완료 보고를 받는다.

### 3. 검증 + 리뷰 — de-tester, de-reviewer를 **병렬로** 실행
- de-tester: 변경 파일 구문 검증 + 기능 시뮬레이션(엣지 케이스 포함).
- de-reviewer: `git diff` 기준 결함·규칙 위반 리뷰.

### 4. 수정 반복 (최대 2회)
- 실패/지적 사항이 있으면 목록을 정리해 de-coder에 다시 위임 → 3번 재실행.
- **2회 반복 후에도 실패**하면: 변경을 커밋하지 말고 `git checkout -- .`로 되돌린 뒤, 백로그 항목에 `⚠ 자동처리 실패(사유)` 를 표시하고 다음 사이클로 넘긴다.

### 5. 마무리 (통과 시)
1. `DEV_BACKLOG.md`에서 해당 항목을 `- [x]`로 체크하고 완료 날짜를 붙인다.
2. `DEV_LOOP_LOG.md` 맨 위에 항목 추가: 날짜 / 항목 / 결과(통과·실패) / 변경 파일 / 특이사항 3줄 요약.
3. 변경 전체를 명확한 메시지로 커밋하고 지정된 작업 브랜치에 푸시한다.
4. 사용자에게 3줄 이내로 결과 요약을 남긴다.

## 원칙
- 사이클당 1건 — 작게, 자주. 항목이 너무 크면 백로그에서 쪼개서 하위 항목으로 만든 뒤 첫 조각만 처리한다.
- 게임 디자인 결정(밸런싱 수치, 레벨 디자인 의도)이 필요한 항목은 구현하지 말고 `❓ 결정 대기`로 표시 후 건너뛴다.
- 세이브 포맷을 깨뜨릴 수 있는 변경은 마이그레이션 코드 없이는 통과시키지 않는다.
- 대규모 리팩터(여러 시스템에 걸친 변경)는 자동 처리 대상이 아니다 — `❓`로 표시하고 사용자에게 영향 범위 요약을 남긴다.
